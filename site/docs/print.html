Dubnium

Dubnium Documentation

Operator entrypoint for installing, bringing up, and understanding the Dubnium workstation and AI control plane.

Dubnium is a rebuildable workstation and AI control-plane experiment for local-first developer workflows, model routing, memory-assisted tooling, and governed automation. It explores how a personal machine can be treated as a coherent operating environment instead of a loose collection of tools: reproducible configuration, explicit modes, local-first AI, reusable context, and policy-aware automation.

Note: Internal documentation provides substantially greater depth on all topics. This external guide covers concepts at a summary level.

AI Control Plane

The AI control plane makes model usage intentional by routing every inference request through policy, not through hard-wired client configuration. Dubnium explores an AI control plane for routing local and remote model use through explicit policy instead of wiring every client directly to every provider.

Design goals

  • Intentional model selection — workloads declare capability requirements; the control plane resolves them to a provider and model instead of each client choosing its own endpoint.
  • Workload separation — interactive chat sessions and batch background jobs use separate queues and resource pools so neither starves the other.
  • Local-first by default — when a local model can serve the request, it should. Remote providers are fallbacks for capability gaps, not the primary path.
  • Governed tool access — tool calls pass through an authorization gate that checks policy before execution.
  • Reviewable evidence — every request, routing decision, and tool invocation leaves traceable records for audit and debugging.

Routing model

The control plane does not ship baked-in provider wiring. It uses a routing layer that maps capability requirements to available providers (local LLM servers, remote APIs, or specialized backends) based on runtime policy. This makes the routing surface declarative and auditable rather than scattered across client code.

Service stack

The control plane includes:

  • An LLM server runtime for hosting local models (backends like vLLM)
  • A model seed system for populating the local model cache
  • A scheduling and automation layer for batch inference and recurring tasks
  • A memory service for persistent context (see Memory)

Why it matters

AI tooling tends to sprawl across editors, terminals, agents, scripts, and services. Dubnium treats that sprawl as an operating-surface problem: clients should have clear routes, workloads should have clear posture, and automation should be observable enough to understand later.

Public boundary

This page describes the control-plane concept. Provider wiring, endpoint details, local service names, storage paths, and operator commands belong in trusted-operator documentation.

AI Stack Architecture

Dubnium’s AI stack separates the control plane, gateway layer, and model runtimes so the workstation stays stable while AI capabilities evolve.

Clients request AI work through the control plane. An optional routing layer can normalize or redirect requests before they reach model providers.

Runtime selection

Default preference order: control plane → local model → Plano (if enabled) → cloud provider. This preserves local-first behavior while allowing cloud escalation when configured.

Model storage

Model weights stay out of Git, the Nix store, and default ISO closures. The preferred runtime location is /var/lib/dubnium/models, populated from seed media or post-install download.

Network exposure

AI services are high-value targets. Default posture binds local runtimes and gateways to localhost. Tailscale or LAN exposure requires explicit per-service flags. Raw Ollama, LLM server, or Plano endpoints should not be exposed when the AI control plane can enforce a policy boundary.

LLM Routing Gateway

Dubnium supports optional LLM routing between local and cloud providers. The routing layer sits beneath the AI control plane and handles provider selection, request normalization, and fallback behavior.

Architecture

AI control plane / clients
  -> routing layer (optional)
    -> local LLM server
    -> cloud provider: OpenAI, Anthropic, etc.

The routing layer is optional — the control plane can call providers directly. Enable routing when you need provider fallback, request normalization across providers, centralized route policy, or model quality tiers.

Implementations

Plano is the primary Dubnium-packaged routing gateway. Dubnium owns the systemd service lifecycle, compute target integration, and local model endpoint wiring. User-level client configuration lives in dotfiles.

model-router (separate repository) provides route-decision semantics, policy schemas, and governance-oriented routing design. Plano consumes these policies at runtime.

Defaults

Plano binds to 127.0.0.1:12000 by default and assumes the local LLM server is on port 8000. Tailscale exposure is opt-in and disabled by default. The service fails closed if the configured executable is missing.

Security

Keep exposeOnTailscale disabled until the gateway behavior is validated. Do not store cloud provider secrets in generated config. Prefer environment files managed by sops-nix. Fallback between models must not bypass privacy, budget, safety, or approval failures — those are policy failures, not retry events.

Memory

Dubnium treats memory as reusable project context for AI-assisted workflows — information that can be classified, governed, retrieved, and reviewed instead of repeatedly rediscovered.

Why memory matters

Without structured memory, every AI interaction starts from zero. Context from previous sessions — project decisions, architectural constraints, operational patterns — is lost or must be re-injected manually. Dubnium’s memory system captures that context, classifies it, and makes it available to future interactions under explicit policy control.

Key ideas

  • Classification before reuse — not all context is equal. Memory items are classified by type (decision, constraint, observation, procedure) so retrieval can match the right context to the right request.
  • Explicit lifecycle — memory moves through stages: ephemeral observation, working context, archived reference, and eventual eviction. Promotion between stages is governed, not automatic.
  • Governed retrieval — the system checks policy before returning stored context. Sensitive context requires stronger authorization.
  • Evidence for review — every memory write, promotion, and retrieval leaves an audit trace.

Architecture sketch

The memory system consists of:

  • A memory service that stores and retrieves context items with typed schemas
  • A classification layer that assigns category and sensitivity labels on ingestion
  • A promotion lifecycle that moves context through stages based on usage patterns and policy rules
  • A governance layer that checks authorization before retrieval or promotion

Why it matters

Agentic workflows depend on context. Without a memory model, that context becomes ad-hoc state spread across prompts, notes, databases, generated files, and tool outputs. Dubnium uses memory as an explicit design surface so context can be useful without becoming invisible operational risk.

Public boundary

This page describes the conceptual memory model. Storage layout, schemas, retrieval behavior, promotion rules, and operational procedures belong in trusted-operator documentation.

Memory Principles

Dubnium memory is a classified lifecycle system for operational and knowledge context. It is not primarily a vector store, RAG pipeline, database table, or runtime cache.

1. Memory is classified, not accumulated

Every durable memory candidate should be classified before persistence — by layer, type, sensitivity, scope, authority, confidence, retention policy, and validation status. Unclassified memory is operational residue, not durable knowledge.

2. Storage is an implementation detail

Postgres, pgvector, Redis, embeddings, and indexes are substrate choices. The durable design concepts are classification → stewardship → lifecycle → policy-aware retrieval. A storage backend is only correct if it preserves those semantics.

3. Operational state is disposable

Operational memory (active plans, tool outputs, workflow checkpoints) should usually expire, be summarized, or be discarded. It should not silently become durable project knowledge.

4. Knowledge is curated

Knowledge memory (decisions, stable facts, lessons learned) requires stronger classification, provenance, confidence, and scope than operational memory.

5. Canonical knowledge lives in version control

Project truth belongs in docs, ADRs, runbooks, and specs. Normal memory rows are not the final authority.

6. Retrieval is policy-bound

A supervisor or control surface should declare requester, purpose, scope, sensitivity limits, and verification requirements. The memory service returns bounded candidates and records retrieval events. Final context assembly belongs outside the memory service.

7. The Memory Steward recommends but does not authorize

The steward may extract, classify, detect duplicates, and recommend promotion. It must not authorize access, bypass policy, blindly persist memory, or assemble final task context.

8. Durable memory is opt-in

Sensitive or ambiguous inputs should remain operational, be summarized, or be rejected unless policy allows persistence.

9. Memory must remain explainable and auditable

A future operator should be able to answer why a memory exists, what produced it, why it was retained and retrieved, and what policy allowed it. Memory operations should create enough provenance and event metadata for replay and review.

10. Every memory has scope, provenance, and a lifecycle

Scope prevents cross-project contamination. Provenance distinguishes durable knowledge from unexplained context. Lifecycle states (candidate → operational → knowledge → archived) prevent the system from becoming a liability.

11. Derived indexes are rebuildable state

Embeddings and vector indexes are retrieval aids, not source of truth. Deleting a memory record must also update derived indexes.

Scheduling and Automation

Dubnium schedules local timed jobs and optional workflow automation alongside the AI control plane.

Why scheduling matters

AI batch inference, model maintenance, context re-indexing, and routine host tasks all benefit from scheduled execution. Without a clear scheduling boundary, cron entries scatter across the system and automation becomes the source of host truth rather than a convenience layer.

Scheduling model

  • Local scheduler owns timed execution on the host — periodic tasks, batch inference jobs, and maintenance windows. It keeps the schedule attached to the machine that runs it.
  • n8n workflow orchestration provides an optional higher-level automation layer for multi-step pipelines, credential-bearing integrations, and webhook-driven flows. Not every host runs n8n.
  • Boundary discipline — the scheduler and n8n do not become the source of host truth. Declarative configuration stays in the Nix flake; schedules reference it but do not replace it.

Relationship to the control plane

The AI control plane mediates agentic or credential-bearing scheduled work. A scheduled inference job routes through the same policy layer as an interactive request, so the governance model applies uniformly regardless of invocation method.

Architecture

Dubnium organizes a NixOS workstation around operating modes, composable profiles, and a control plane that separates interactive and background workloads. It treats a workstation as a governed operating environment: reproducible configuration, explicit runtime posture, local-first AI, and controlled automation.

System themes

The public architecture view is organized around a few ideas:

  • Rebuildability: the system should be recoverable from declared configuration and source-controlled intent.
  • Operating modes: interactive, compute, automation, and AI workloads should not silently compete for the same resources.
  • Local-first AI: local model use should remain practical while still allowing external model routing when appropriate.
  • Governed transitions: changes in posture should be explicit, observable, and reversible.
  • Layered ownership: system configuration, user configuration, runtime state, and generated artifacts need clear boundaries.

Operating modes

A mode defines the runtime character of the system — whether it behaves as a desktop workstation, a headless AI compute node, a development environment, or some combination. The system boots into a configured default mode and can transition between modes at runtime. Modes control which services are active, what resources are allocated, and how the system responds to workload demands. This prevents AI batch jobs from competing with interactive desktop use and keeps the automation surface intentional.

Profiles

Profiles are opt-in named sets of services. Only the minimal base profile is active by default. Additional profiles enable:

ProfilePurpose
graphicalDesktop environment, display server, input
studioCreative and development tooling
AILLM serving, model routing, memory
computeBatch processing, CI runners, k3s

Profiles compose — you can enable AI on a graphical system or run a headless compute node with no desktop at all.

Host composition

The repository builds installable NixOS configurations for multiple targets: a physical workstation, a headless VM for validation, WSL on Windows, and container hosts. Shared modules live in the flake and are composed per-target, so the same AI stack works across form factors with target-specific hardware configuration.

Control plane

The control plane routes AI tooling through explicit policies rather than wiring clients directly to model endpoints. This allows:

  • Intentional model selection per workload
  • Separation of interactive and batch inference
  • Local-first workflows that degrade gracefully when offline
  • Governed tool access that preserves audit evidence

AI Architecture

Dubnium’s AI stack routes every inference request through policy rather than hard-wired client configuration. The architecture keeps policy and routing above raw model runtimes, supports local-first execution with explicit cloud escalation, and prevents direct exposure of high-value AI endpoints by default.

Core rule

Clients request AI work through a control plane.
Gateways route.
Runtimes generate tokens.

Only one layer owns a decision at a given abstraction level.

Layer model

LayerOwnsMust not own
ClientsUser and workflow requestsProvider policy, direct memory access
AI control planePolicy, provider selection, tool governanceRaw inference runtime concerns
Routing gatewayRequest normalization, backend routingAgent governance, memory policy
Model runtimesToken generation, streaming, model lifecycleTool governance, durable memory
Cloud providersRemote model executionLocal operator policy

Paths

  • Default path: client → control plane → local LLM server
  • Routed path: client → control plane → routing gateway → local or cloud backend
  • Escalation path: governed workflows → Hermes → gateway → cloud or local runtime

Exposure boundaries

AI services bind to localhost by default. Tailscale or LAN exposure requires explicit per-service configuration. Raw runtime and gateway endpoints should not become the default operator entrypoint. Automation clients call the configured control plane for agentic or credential-bearing work.

Degraded behavior

The base host remains healthy when no AI services are enabled. If the local LLM server is unavailable, the control plane may escalate to configured cloud providers when allowed. Policy and credential boundaries fail closed — routing fallback must not bypass approval or exposure rules.

Control Plane

The control plane reconciles requested mode intent with runtime facts. It is a local privileged authority, not a convenience shell script.

Authority model

Transition execution is privileged — the operator path is sudo modectl request <mode> or a root-owned systemd service. Unprivileged users must not mutate observed state or forge transition success.

State model

Live state lives under /run/mode-controller: desired mode, current mode, lock, last transition, last guard results, capability placement, and hardware topology. Persistent transition history lives as an append-only JSONL event stream under /var/lib/mode-controller/events.jsonl.

Reconciliation sequence

Every requested transition follows a ten-step sequence: acquire lock, observe current state, validate target, validate capability placement, run guards, execute bounded actions, re-observe, classify final state, record outcome, release lock. If target predicates fail after mutation, the controller attempts rollback or reports a failed transition.

Observer contract

The observer derives current state from evidence only. It must not trust desired state as proof of success. Required signals include graphical session presence, compositor state, target isolation status, service markers, GPU evidence, and controller lock state. The observer reports unknown, transitioning, degraded, or failed-transition instead of pretending a stable target has been reached.

Guards

Guards are small deterministic checks with stable exit codes: 0 for pass, 10-19 for policy block, 20+ for execution error. The initial set covers target reachability, audio idle, graphical session terminability, GPU display release, LLM server drainability, capability presence, memory headroom, and persistence paths.

Failure semantics

Blocked transitions (guard policy block) leave desired state requested without rewriting current state. Execution errors mean a guard or action could not run reliably. Degraded state means the system is usable but does not satisfy all guarantees. Failed transitions mean no stable contract could be established.

Profiles and Modes Architecture

Dubnium distinguishes two related but separate concepts:

  • Mode = current operational state (how the machine is behaving right now)
  • Profile = installed or enabled capability set (what the machine can run)

Keeping them separate prevents overloaded meanings and conceptual drift.

Vocabulary

TermMeaningExamples
ModeRuntime state selected or observed on a hostdesktop, compute
ProfileDeclarative capability bundlebase, graphical, studio, ai, development, compute
TargetDeclarative runtime surface made available by profilesgraphical, ai, compute
ServiceConcrete daemon, timer, or runtime componentllm-server, n8n, github-runner
TierSupport expectation and maintenance priorityTier 1, Tier 2, Tier 3

Mental model

Host
  has Profiles
  enables Targets
  enters Modes
  runs Services

A profile enables a target contract. The mode determines runtime behavior and resource posture. Optional services remain explicit selections rather than implicit profile payload.

Why it matters

Conflating modes and profiles causes drift: compute starts meaning both GPU scheduling and LLM server installation. desktop starts carrying personal configuration and automation services. Keeping the boundary clean means profiles enable capability, targets expose mode surfaces, modes activate runtime posture, and services remain explicit operator selections.

Control-plane relationship

Profiles and modes sit below the control-plane hierarchy: NixOS declarations feed systemd enforcement, which dubctl bridges for operator UX, and the mode controller manages runtime state against services.

Runtime Behavior

Dubnium switches between three host-local modes, each with distinct runtime characteristics.

Modes

desktop — interactive workstation and development mode. Graphical session available, ordinary audio, display GPU protected for UI, LLM server inactive.

studio-local — low-latency audio profile layered on desktop. Audio-priority policy active, AI suppressed, heavy background pressure reduced.

compute — headless throughput mode for AI and platform work. Graphical session absent, compute target active, LLM server active when enabled, AI resources assigned to the configured GPU profile.

Supported transitions

desktop -> studio-local
studio-local -> desktop
desktop -> compute
compute -> desktop

studio-local -> compute routes through desktop unless a future contract allows direct promotion.

Transition semantics

desktop → studio-local: validate studio capability, stop LLM server if active, start audio-priority services, re-observe. Success requires studio policy and audio overlay active, LLM server inactive.

studio-local → desktop: stop audio overlay services, verify desktop target, re-observe.

desktop → compute: the heaviest transition. Validate compute capability, check audio idle, terminate graphical session, release GPU display, isolate compute target, start LLM server, re-observe. Success requires compute target active, graphical session absent, LLM server active, GPU ownership evidence matching the compute profile.

compute → desktop: drain and stop LLM server, isolate desktop target, restore graphical session, re-observe. Rollback validated through the same post-action observation rules.

Dubnium is accumulating useful but unevenly mature capabilities. Support tiers keep useful experiments from destabilizing the base system.

Promotion criteria

Client Architecture

Dubnium distinguishes host composition (what the machine runs) from client architecture (how users and tools reach the machine).

Client classes

  • Local workstation — interactive user session on the host itself
  • Remote admin — laptop or secondary machine over Tailscale
  • Phone or secondary device — limited access for status checks
  • Automation clients — n8n workflows, CI-triggered jobs, scheduled tasks

Boundaries

Clients do not define host truth — the flake does. Clients should prefer bounded entrypoints (the control plane, dubctl, modectl) over ad hoc service access. Remote admin access follows the VPN and service exposure architecture. Credential-bearing or agentic clients should route through the AI control plane rather than calling providers or runtimes directly.

Memory Architecture

Dubnium treats durable memory as classified application data, not just infrastructure state. Storage technology does not define the memory model — the conceptual layering and governance do.

Core rule

The local LLM server is the inference runtime.
Persistent memory is a separate classified lifecycle subsystem.

Conceptual layers

LayerQuestionExamplesLifecycle
OperationalWhat am I doing?Session context, plans, tool outputsExpire or summarize
KnowledgeWhat do I know?Decisions, stable facts, lessons learnedCurate, review, archive
CanonicalWhat is project truth?Docs, ADRs, runbooks, specsVersion in repo

The promotion boundary between operational and knowledge memory is the highest-risk part of the system — active planning should not become durable knowledge without classification and review.

Data classes

Dubnium distinguishes source artifacts, memory records, policy envelopes, embeddings, indexes, context packets, and workflow state — each with its own canonical owner. Embeddings and indexes are derived, rebuildable state, not the source of truth.

Policy envelopes

Memory lifecycle needs separate policy questions per operation:

  • Read policy — may this actor retrieve these candidates for this purpose?
  • Write policy — may this candidate become a memory record?
  • Promotion policy — may operational memory become knowledge?
  • Retention policy — should this memory expire or be reviewed?
  • Deletion policy — may this memory and its derived indexes be removed?

Ownership boundaries

Dubnium hosts the memory service infrastructure. External governance tools evaluate access and promotion rules. The AI control plane assembles context from approved memory candidates. Vector indexes are rebuildable derived state. Canonical knowledge lives in versioned documentation.

Local Override Convention

Dubnium supports several gitignored override points so operators can add host-local packages, user-local Home Manager config, installer secrets, and generated machine state without dirtying tracked source or forking the flake.

Five conceptual layers from closest to the machine to closest to the user:

When to use which

  • Temporary system experiment → Layer 0 (local/dubctl-packages.nix)
  • Host-specific durable override → Layer 1 (hosts/<host>/user.local.nix, copied from hosts/user.example.nix)
  • State that survives repo re-clone → Layer 2 (/etc/dubnium/local/generated.nix)
  • Temporary user-level package → Layer 3 (git-local.nix)
  • Per-machine display, scaling, aliases → Layer 4 (~/.config/<tool>/local.*)

Tool boundaries

dubctl writes only Layer 2. configctl governs only Layer 4. Layers 0, 1, and 3 are hand-edited. The goal is to promote durable choices into versioned config after 2-3 stable rebuilds. Machine-specific state (GPU topology, disk layout) stays in Layer 1 or 2 permanently.

Service Exposure Architecture

Dubnium services follow a tiered exposure model that defaults to localhost-only and requires explicit configuration for broader access.

    -> safest default

    -> explicit private remote access

LAN
    -> exceptional, service-specific justification required

Policy

Services bind to localhost by default. Tailscale exposure is explicit and documented per service. LAN exposure is exceptional and must be justified service-by-service. Public ingress is not part of the default Dubnium posture.

Services in scope include the local LLM server, n8n, the memory API, GitHub runner endpoints, and future optional services. Each service that broadens its bind address beyond localhost should document the authentication and trust assumptions it relies on.

Dubctl — Host Operator UX

dubctl is Dubnium’s narrow operator helper for common host-local operations — service enablement, capability management, flake input manipulation, package overrides, AI diagnostics, GPU monitoring, and NixOS rebuild orchestration.

It is not a second configuration control plane. It writes bounded host-local selection state that NixOS sees at rebuild time, keeping the flake as the source of truth for architectural wiring.

Key capabilities

  • Service management — list, enable, and disable registered services with optional profile bindings and settings. Mutations require root.
  • Capability management — enable or disable registered integration and capability selections.
  • Flake input management — list, search, add, remove, and update flake inputs without editing Nix source by hand.
  • Local package overrides — inspect and manage local system package attrs outside the flake.
  • AI diagnostics — report provider and system diagnostics, delegate analysis to the AI control plane.
  • GPU monitoring — watch NVIDIA GPU utilization by role or profile (read-only wrapper around nvidia-smi).
  • Apply — run nixos-rebuild for the declared Dubnium state with automatic local path overrides.

External command trees

dubctl can dispatch a user-owned command subtree from $PATH. Executables use the naming convention dubctl-<token>-<token>, where each command token is lowercase ASCII alphanumeric text, and receive the remaining arguments unchanged:

dubctl meeting session start --foo
  -> dubctl-meeting-session start --foo

The longest matching executable prefix wins. Built-in commands and aliases always take precedence. Resolution uses direct argv execution, never a shell, and is disabled for privileged execution, including UID transitions and effective UID 0. Plugins should own their own state and communicate with dubctl through argv, environment, stdin/stdout/stderr, exit codes, and signals.

The initial intended consumer is a Home Manager-installed dubctl-meeting-session command for graphical user-session lifecycle actions.

The current source-file split is not itself treated as an architectural boundary. Later migrations must identify each command’s use cases, narrow ports, system adapters, privilege/session requirements, state ownership, and independent packaging value before removing static parser wiring.

Discovery and external help

Use dubctl commands to inspect the unified command surface. The human output contains logical paths, whether each entry is built-in or external, its selection state, and the selected executable path. Use dubctl commands --format json for a versioned machine-readable inventory:

{"schemaVersion": 1, "commands": []}

External entries can be inspected without knowing their executable name:

dubctl help meeting session

This forwards --help to the selected external executable. Discovery and help forwarding use the same privilege/trust policy as normal external dispatch.

Home Manager integration

A user-session plugin can be installed without changing Dubnium’s core package:

{ pkgs, ... }:
{
  home.packages = [
    (pkgs.writeShellApplication {
      name = "dubctl-meeting-session";
      text = ''
        case "''${1-}" in
          --help)
            echo "usage: dubctl meeting session {start|stop|status}"
            exit 0
            ;;
          --version)
            echo "dubctl-meeting-session 0.1.0"
            exit 0
            ;;
        esac
        exec my-session-use-case "$@"
      '';
    })
  ];
}

The plugin owns its application state, graphical-session adapters, and domain use cases. It communicates with dubctl only through argv, environment, stdin/stdout/stderr, exit status, and signals. Read-only verbs such as status must not mutate state. Machine-readable output should use a versioned envelope such as { "schemaVersion": 1, "command": "meeting session status" }.

Safety model

dubctl treats command arguments as untrusted input, validates Nix attr safety, backs up flake.nix before mutation, and uses argv arrays instead of shell string concatenation. Service and capability mutations require root; listing and diagnostics do not.

Boundaries

dubctl may manage generated host-local state and invoke nixos-rebuild. It must not become the owner of source-controlled policy, manage user home layering (that is configctl’s domain), store secrets, or edit service-specific app state.

Configctl — Home Configuration Reconciliation

configctl is a generic home-configuration reconciliation CLI for managing layered home config, init contracts for first-run tool state, and drift detection. It is not Dubnium-specific — usable on any Linux machine with layered dotfiles.

Layer model

Per-tool home configuration is organized into ownership layers under ~/.config/<tool>/:

  • managed.* — generated by Home Manager or dotfiles; never edit directly
  • local.* — machine-specific overrides; never automatically promoted
  • custom.d/ — user-authored fragments that are candidates for promotion to dotfiles
  • adopted.d/ — fragments already promoted or represented by managed config

Key capabilities

  • status — inspect layering state for one or all tools
  • adopt — scaffold the layered directory structure for a tool
  • promote — copy a custom fragment into the dotfiles repo and stage it
  • reconcile — detect drift between dotfiles and local custom fragments
  • doctor — environment health check for required tools and init contracts
  • init — manage first-run tool-state contracts (npm globals, pip packages, Hermes config, Codex config) with risk-gated approval
  • git-hooks — declarative git hook management through git config sections

Use case

configctl solves the tension between immutable managed config and the need for local overrides that should not end up in version control. It provides a structured promotion path from throwaway local customization to committed dotfile fragment.

Mode Controller — Runtime Mode Transitions

modectl manages runtime mode transitions between desktop, studio-local, and compute modes. It controls systemd target isolation, GPU and audio resource contention, and guard-based safety checks that prevent unsafe transitions.

Modes

ModeDescription
desktopInteractive workstation. GUI on, local AI off.
studio-localOverlay on desktop for audio-priority policy. AI suppressed.
computeHeadless throughput mode. Graphical session absent, AI services active.

Transitions between desktop and studio-local are lightweight. Transitions to compute isolate via systemd target switching and stop the graphical session.

Guards

Pre-transition safety checks prevent transitions that would disrupt running work. Guards check audio idle state, CPU load, long-running user jobs, memory headroom, GPU display release, and vLLM drainability. Most guards are non-bypassable; the user-jobs check can be bypassed at request time.

Key capabilities

  • status — show current and desired mode, last transition, and guard results
  • request — request a mode transition with optional guard bypass
  • reconcile — run the full reconciliation loop against the desired mode
  • current / desired — print observed or stored mode
  • doctor — environment health check

Architecture

State lives under /run/mode-controller (runtime) and /var/lib/mode-controller (durable event log). Reconciliation runs through a parameterised systemd oneshot service triggered by the request command. Every transition is recorded in an append-only JSONL event stream for audit and diagnosis.
