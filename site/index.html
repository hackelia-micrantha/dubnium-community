Dubnium is a local-first engineering platform for reproducible development, self-hosted CI and governed AI automation.

Built on NixOS, it coordinates development environments, build capacity and model services around available resources, explicit authority and operator-controlled data.

Design approach

Rebuild the system. Govern the work. Keep control of the data.

Most engineering stacks treat developer environments, build infrastructure, AI assistants and security as separate systems. Dubnium explores how to coordinate them without collapsing their trust boundaries. Four design decisions distinguish the platform.

01 / REPRODUCIBILITY

Replace the environment, not the work.

Declare the system and each project's dependencies with Nix. Reuse trusted immutable build outputs while keeping mutable user and application state explicitly owned. Recovery should not depend on undocumented machine history.

Reproducible engineering
02 / EXECUTION AUTHORITY

Give AI capabilities, not credentials.

Separate reasoning, identity, authorization and execution. A valid request or a successful prediction does not grant permission. Governed capabilities and independently verifiable outcomes are the intended boundary for consequential automation.

Governance and safety
03 / RESOURCE ADAPTATION

Make one system serve many workloads.

Interactive development, media, inference and CI compete for finite compute. Runtime modes and bounded worker admission let capacity follow current work, while dynamic planning aims to avoid unnecessary builds rather than weaken required checks.

Runtime operating modes
04 / DATA SOVEREIGNTY

Keep intelligence close to the data.

Prefer local models, scoped memory, private services and local observation. External inference, remote execution and organizational telemetry should cross explicit boundaries. Local operation does not by itself establish privacy or security.

Local-first AI and automation

Platform capabilities

One engineering environment, many independent boundaries.

Reproducible infrastructure, intelligence and governed automation share resources without sharing unrestricted authority. These capabilities span the evolving reference environment, published experimental interfaces and directions under qualification.

01 / AUTHORITY

Governed capabilities

Separate AI proposals, identity, policy and execution. Experimental capability contracts and conformance make authorization and effects inspectable; Keylix and Anthesis provide complementary identity and governance boundaries.

Governance and security
02 / OPERATOR

Operator experience

Composable CLI tools for host workflows, runtime modes, configuration and capabilities. An experimental operator authentication contract supports the direction toward a bounded Operator API and mobile/web consoles, rather than arbitrary remote shell access.

Operator interfaces
03 / INTELLIGENCE

Local-first intelligence

Local inference, model routing and bounded remote escalation. Multi-GPU serving, token-efficient routing, classification and predictive planning are active areas of development and evaluation, not guaranteed savings.

AI and automation
04 / STATE

Memory and scheduled automation

Experimental Memory and Scheduler APIs make reusable context and deferred work explicit. Scope, provenance, state and execution authority remain separate from model reasoning.

Memory and scheduling
05 / DELIVERY

Adaptive CI/CD

Short-lived self-hosted workers, reproducible builds and trusted cache reuse. Dynamic test selection and registry-free ordinary onboarding are directions under evaluation; admission remains governed and resource-aware.

Self-hosted CI
06 / RUNTIME

Runtime and isolation

Desktop, media and compute modes adapt available resources to the workload. Layered VM, container and process isolation is chosen for the threat model rather than presented as one universal sandbox.

Runtime modes
07 / CONNECTIVITY

Private connectivity and deployment

Explore VPN-connected private services, optional edge exit-node integration and replaceable virtual appliances. Router qualification, portable QCOW2 images and cloud appliance delivery remain separate work.

Deployment direction
08 / EVIDENCE

Observability and data sovereignty

Local-first service health, metrics, logs and traceable outcomes support diagnosis without indiscriminate data export. OpenTelemetry interoperability is developing; remote data sharing is explicit.

Goals and outcomes

From engineering evidence to practical adoption.

The next challenge is to turn the reference environment and public contracts into repeatable integration evidence, especially for private AI, reproducible developer endpoints and isolated build infrastructure.

Now

Qualify reproducible, bounded execution and the first public contract bundle.

  • Maintain contract correctness and conformance.
  • Complete release metadata, provenance and downstream acceptance.
  • Demonstrate repeatable integration and verification with public-safe examples.

Next

Make independent adoption and integration easier.

  • Test contracts against independent and downstream implementations.
  • Develop event and resource-budget interoperability contracts.
  • Refine compatibility guidance from adopter feedback.

Later

Validate practical adoption and deployment opportunities.

  • Evaluate supported deployment patterns with independent users.
  • Use integration evidence and partner feedback to guide further work.
