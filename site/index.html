Overview

Dubnium asks how an engineering environment should behave when it must be replaceable, observable, secure, useful for interactive development, and able to host or call automation without giving every tool ambient authority.

The architecture can be composed as smaller client environments, richer workstations, build or compute nodes, remote managed environments, and stronger security or administrative environments. The public model describes responsibilities and trust boundaries rather than production topology.

Runtime operating modes

A reproducible endpoint does not need every declared capability active simultaneously. modectl selects which declared workload set should be active, runs guards, reconciles the transition, verifies observed state, and records the result.

desktop

Normal interactive engineering mode. Graphical and developer-facing workloads take priority while compute-oriented AI workloads remain suppressed by mode policy.

studio-local · media

Interactive media mode. The desktop stays available while media-priority policy suppresses competing compute workloads.

compute

Dedicated compute and local-AI mode. Graphical work is released so compute-oriented services can receive the resources they require.

modectl status
modectl request desktop
modectl request studio-local
modectl request compute

studio-local is the current runtime identifier for media mode; older internal service names may still say studio or audio. Runtime modes choose among declared capabilities; they do not rewrite the NixOS definition, widen authorization, or bypass capability policy.

Writable user configuration

NixOS-managed configuration is often backed by the immutable Nix store and should be regenerated rather than edited in place. The user environment itself is not globally read-only.

configctl provides an explicit writable boundary for applications and user preferences, then makes drift and promotion back into declarative configuration visible.

Managed reviewed declarative defaults; regenerated instead of edited in place.
Local writable machine-specific overrides that remain local.
Custom writable user fragments that can later be reviewed and promoted.
Adopted fragments already represented by managed configuration and retained as reconciliation history.
user or application writes a setting
→ configctl reports ownership and drift
→ portable change is reviewed and promoted
→ rebuild makes it the managed default

This keeps the base system reproducible without forcing legitimate application preferences, local customization, or first-run mutable state into ad-hoc system mutation.

System themes

Reproducibility

Declared platform, user, and project environments make endpoints easier to rebuild, replace, review, and audit.

Observability

Desired state, observed runtime state, durable domain state, and bounded evidence remain distinct and inspectable.

Governed capabilities

Identity and connectivity inform policy, while privileged effects still require explicit bounded authority.

AI and automation

Models can propose intent while deterministic validation, policy, lifecycle state, and effect execution remain explicit.
